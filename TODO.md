## A4. Графики ранга и uptime всегда начинаются с выдуманного нуля (B10)

**Где:** `src/servers/servers.service.ts:253-281` (`findRankChart`), `:344-369` (`findUptimeChart`, ветка 3d/7d/30d).

**Проблема.** Слоты строятся от полуночи первого дня (`DATE_TRUNC('day', date_from)`), а записи рейтинга берутся с `calculated_at >= date_from`, где `date_from = NOW() − N дней` — середина дня. Рейтинг считается в 00:00 UTC, поэтому запись первого дня всегда отсекается. Пример: сейчас 10.11 15:30, период 3d → слоты 7, 8, 9, 10 ноября; записи есть за 8, 9, 10; слот 7 ноября получает `COALESCE(…, 0)` — ранг 0, uptime 0 %, downtime 100 %. Так у каждого сервера на каждом периоде.

**Что сделать.**
1. В обоих запросах в CTE `daily` заменить условие на `calculated_at >= DATE_TRUNC('day', (SELECT date_from FROM period))`.
2. Для дней без расчёта отдавать `null`, а не 0: убрать `COALESCE` у `rank`, `score`, `uptime_ratio`; `downtimeRatio` тоже `null`, если нет данных (`1 - NULL` в SQL даёт `NULL` само).
3. Убрать превращение `null` в 0 в JS. `Number(null)` равен 0, поэтому одного SQL мало. Таких преобразований пять, в двух `map`:
   - `findRankChart`, `:292-297`: `rank`, `score`, `uptimeRatio`;
   - `findUptimeChart`, `:380-384`: `uptimeRatio`, `downtimeRatio`.

   Каждое заменить на проверку вида `r.rank === null ? null : Number(r.rank)`. Типы строк запроса (`:284-289`, `:373-377`) — `number | null`.
4. В `dto/server-response.dto.ts` (`:54-69`) пометить эти пять полей как `nullable: true` и `number | null`.
5. Ветку `24h` в `findUptimeChart` не трогать: там `COALESCE(…, 0)` верный — нет записи значит 0 игроков.

**Проверка.** `npm run build`. Мысленный случай из примера: слот 7 ноября получает запись от 7.11 00:00. Для сервера без единого расчёта рейтинга все точки 3d/7d/30d приходят как `null`, ни одна — как 0.

**Связи.** Меняет форму ответа: во Frontend парное замечание A4f (типы и отрисовка `null`). Обновить таблицу «API» в `CONTEXT.md`.

## A5. Последняя точка графиков за 24 часа — ложный провал (B9)

**Где:** `src/servers/servers.service.ts:196-211` (онлайн, 24h), `:222-226` (онлайн, 3d/7d/30d), `:313-326` (uptime, 24h).

**Проблема.** Ряд слотов доходит до текущего часа и текущей 15-минутки включительно, а они ещё не закончились.
- Uptime 24h: в 15:10 за текущий час есть один слот из четырёх → последняя точка 25 % у здорового сервера.
- Онлайн 24h: в 15:00:20 сбор ещё не дошёл до игры → последняя точка 0 игроков.
- Онлайн 3d/7d/30d: в первые минуты часа последняя точка тоже 0.

**Что сделать.** Заканчивать ряд последним завершённым интервалом:
- онлайн 24h: от `текущий слот − 24 ч` до `текущий слот − 15 мин` включительно — ровно 96 точек;
- онлайн 3d/7d/30d: до `date_trunc('hour', NOW()) − 1 час` — ровно `N × 24` точек;
- uptime 24h: `date_from = date_trunc('hour', NOW()) − 24 часа`, `date_to = date_trunc('hour', NOW())` — 24 полных часа.

**Проверка.** `npm run build`. Число точек: 96, 72, 168, 720 и 24.

**Связи.** Закрывает B9 и расхождение с отчётом («ровно 96 и 168 точек», таблица в `../PROJECT.md`). Число точек меняется на одну — Frontend от числа точек не зависит, но проверьте `ServerChart.tsx`.

## A7. Страницы списка серверов повторяют и пропускают строки

**Где:** `src/servers/servers.service.ts:79-86` (`findAll`).

**Проблема.** Список сортируется по `players`, `name` или `rank` и режется через `OFFSET`. У тысяч серверов одинаковые `players` или `rank = 0`, а порядок среди равных PostgreSQL не гарантирует. Один и тот же сервер может попасть на страницу 1 и на страницу 2, а другой — ни на одну.

**Где это видно пользователю.** Страница сайта `/games/:id` (список серверов игры) — сортировка по колонкам Rank, Server Name, Players Online и кнопки страниц ‹ ›. Каждая страница — отдельный запрос к API и к базе, и в каждом запросе порядок равных серверов может получиться свой. Пользователь листает страницы и видит один и тот же сервер дважды, а часть серверов не видит никогда. То же у любого клиента API, который проходит `GET /servers` по страницам.

**Замер на живом API 12.11.2026 06:30 UTC.** Enshrouded (`appid=1203620`, 2 887 серверов), все страницы по 100 строк подряд:
- `sortBy=players&sortOrder=desc` — получено 2 887 строк, из них уникальных `id` только 2 008: 879 серверов пришли повторно и 879 не пришли ни на одной странице (у игры всего 10 разных значений `players`);
- `sortBy=rank` (сортировка по умолчанию) — 13 повторов и 13 пропусков. Сейчас у всех серверов `rank = 0` (первый рейтинг — 14.11), то есть весь список — одна группа равных.

**Что сделать.** После основной сортировки добавить `qb.addOrderBy('server.id', 'ASC')` в обеих ветках. Одна строка.

**Проверка.** `npm run build`. На стенде: `sortBy=players`, пройти первые 10 страниц — ни одного повторяющегося `id`.

**Связи.** Нужно до публичного API (K3.1) и до keyset-пагинации (B3) — та тоже опирается на `id` как на последний ключ. **Делать до A6 в Worker или вместе с ней:** после A6 у каждого офлайн-сервера `players = 0`, это тысячи равных значений в каждой игре, и повторов при сортировке по игрокам станет ещё больше.

## A16b. Неиспользуемая сущность `OnlineRecord` (B12)

**Где:** `src/servers/online-record.entity.ts` (27 строк), ссылки в `src/app.module.ts:8,26` и `src/servers/servers.module.ts:4,10`.

**Что сделать.** Удалить файл и четыре ссылки на него. Перед удалением проверить `grep -rn OnlineRecord src`.

**Проверка.** `npm run build`. В `CONTEXT.md` убрать файл из дерева структуры и строку про расхождение индекса.

## A18. Слишком большой `id` или `appid` даёт 500

**Где:** `src/servers/servers.controller.ts:29,37,47,57` (`ParseIntPipe`), `src/games/games.controller.ts:36`, `src/servers/dto/query-servers.dto.ts:16-19,86-89`.

**Проблема.** `ParseIntPipe` и `@IsInt()` пропускают любое целое. `GET /servers/99999999999` доходит до PostgreSQL и падает с `value out of range for type integer` — клиент получает 500 вместо 404. То же с `?appid=99999999999`.

**Проверено на живом API 12.11.2026:** `GET /servers/99999999999` → 500, `GET /servers?appid=99999999999` → 500. Третий случай, которого не было в первом аудите: `GET /servers?appid=221100&page=99999999999999999999` → 500 — у `page` есть `@Min(1)`, но нет верхней границы, и `OFFSET` выходит за пределы `bigint`.

**Что сделать.** В DTO добавить `@Min(1)` и `@Max(2147483647)` к `appid`. К `page` в обоих DTO списков (`query-servers.dto.ts:21-26`, `games/dto/query-games.dto.ts:24-29`) добавить `@Max(1000000)` — любая разумная граница. Для параметров пути — один общий pipe с той же проверкой вместо голого `ParseIntPipe` (ответ 400).

**Проверка.** `npm run build`. `GET /servers/99999999999` → 400, `GET /servers/2147483647` → 404, `GET /servers?appid=221100&page=99999999999999999999` → 400.

**Связи.** Удобно делать вместе с единым форматом ошибок (K3.1).

## A2b. Почасовой uptime делит на 4, а не на число удавшихся циклов

**Где:** `src/servers/servers.service.ts:323-331`.

**Проблема.** `LEAST(COUNT(*) / 4.0, 1.0)` считает, что в каждом часе было четыре цикла сбора. Если цикл для игры не удался (ошибка Steam), все серверы игры показывают 75 % uptime за этот час.

**Что сделать.** Делить на число удавшихся циклов игры в этом часе: `COUNT(DISTINCT recorded_at)` по записям серверов той же игры (`servers.appid` сервера `$1`).

**Связи.** Только если в Worker сделана A2.2 — формулы должны совпадать. По наблюдению Валерия (10.11.2026) сбоев сбора не было, так что замечание можно не делать, пока они не появятся в логах.

## A3b. Почасовой график усредняет только непустые точки

**Где:** `src/servers/servers.service.ts:228-236` (`AVG(r.players)` по часу).

**Проблема.** Сервер с 40 игроками в одном слоте из четырёх показывает за час 40, а не 10. Подробности — A3 в `../Serverscope-Worker/TODO.md`.

**Что сделать.** В ветке 3d/7d/30d заменить `AVG(r.players)::int` (`:230`) на `(SUM(r.players) / 4.0)::int`. Одна строка. Константа 4 — число циклов сбора в часе, то же допущение, что в A3.1 у Worker и в `/ 4.0` у почасового uptime. Ветку `24h` не трогать: там одна точка на слот.

**Условие.** Это верно, только пока в `online_records` лежат одни сырые 15-минутные точки, то есть пока прореживание выключено (A20 в Worker, вопрос 8 в `../TODO.md`). Если очистку вернут в расписание в старом виде, сырые и почасовые строки снова смешаются в одной таблице, и делить на 4 станет нельзя — тогда замечание откладывается до новой почасовой таблицы (K1.1). Перед правкой проверьте статус A20 и ответ на вопрос 8.

**Проверка.** `npm run build`. Случай: за час у сервера одна запись с 40 игроками → точка графика 10.

**Связи.** Выкатывать вместе с A3.1 в Worker: иначе спарклайн в списке и график на странице сервера покажут разные числа за один и тот же час. После K1.1 график 3d/7d/30d читается из новой почасовой таблицы.
